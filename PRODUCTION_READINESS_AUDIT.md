**Trading Bot audit — 10 October 2026 (Asia/Kolkata)**

**Verdict: this project is not ready for real-money trading. Its data and execution displays are not entirely genuine.** It combines implemented trading infrastructure and a useful paper simulator with fabricated market information, misleading success messages, incomplete broker integration, and strategy inconsistencies. The available results do not establish that any strategy is profitable.

Reviewed repository revision `3179de0`, initially with a clean working tree. Scope included the API, worker, domain calculations, strategy engine/backtester, frontend trading controls, Daily Bot, broker adapters, risk controls, deployment scripts, and relevant tests. This was a source review and local validation; no real broker account connection or order was made. Findings describe the checked code, not a separately running deployment or its actual account state. I edited only this report. Concurrent workspace edits to `schemas.ts`, `backtest-engine.ts` and `strategies.tsx` appeared during the review; I preserved and inspected them, updated the affordability finding, and reran validation.

**Critical findings — resolve before any live trading**

1. **The UI can falsely confirm that exposure has been closed.** In [useWorkstation.ts](/Users/user/Documents/Projects/TRADING-BOT/apps/trader/src/hooks/useWorkstation.ts:140), flattening immediately sets positions/reservations to zero and cash to ₹10,000. If the API fails, the catch returns `success: true` and says positions were closed. Emergency stop and disarm calls also swallow errors. [orders.tsx](/Users/user/Documents/Projects/TRADING-BOT/apps/trader/app/orders.tsx:121) submits a close request without awaiting confirmation, fabricates an exit order and P&L, and announces that the position closed and GTT was cancelled. A failed network request can therefore leave the screen showing safety that the backend/broker never confirmed. Preserve exposure and show pending/failed state until confirmed exit fills reconcile.

2. **Some frontend executions are entirely local simulations.** [orders.tsx](/Users/user/Documents/Projects/TRADING-BOT/apps/trader/app/orders.tsx:180) handles “Supervised Execute” by inserting a hardcoded 25-unit fill at ₹124, a `UPSTOX_SIM_...` ID, and a `PROTECTED_GTT` position into React state. It makes no execution request in that handler. [proposals.tsx](/Users/user/Documents/Projects/TRADING-BOT/apps/trader/app/proposals.tsx:66) marks proposals approved before the response; its failure branch claims freshness validation, locked capital and attached GTT protection. Approval and execution also need distinct states: successful proposal approval alone does not prove a fill or protective order.

3. **Live supervised execution invents fill confirmation.** [supervised-execution.service.ts](/Users/user/Documents/Projects/TRADING-BOT/apps/api/src/orders/supervised-execution.service.ts:176) moves an accepted order to `FILLED`, takes quantity and price from the proposal, commits its reservation, and proceeds to protective orders. It does not first query/receive actual broker fill quantity and weighted price. Accepted, pending, partially filled, cancelled and rejected-after-acceptance orders need separate broker-confirmed handling. An exception during dispatch can also release a still-HELD reservation although the broker result is ambiguous ([catch](/Users/user/Documents/Projects/TRADING-BOT/apps/api/src/orders/supervised-execution.service.ts:325)); committed reservations are protected by the manager's release guard, but this does not solve ambiguity before commit.

4. **The live adapter does not match current broker order interfaces.** [upstox-broker.adapter.ts](/Users/user/Documents/Projects/TRADING-BOT/apps/api/src/broker/upstox-broker.adapter.ts:260) places V3 orders through `UPSTOX_BASE_URL` rather than the configured HFT URL, omits the JSON Content-Type header, reads singular `data.order_id`, and invents an ID when absent. The official V3 interface returns an `order_ids` array. Losing the real IDs prevents reliable order lookup/cancel/reconciliation. See [Upstox Place Order V3](https://upstox.com/developer/api-documentation/v3/place-order/).

   Its [GTT payload](/Users/user/Documents/Projects/TRADING-BOT/apps/api/src/broker/upstox-broker.adapter.ts:395) omits transaction direction and per-rule `trigger_type`, and assumes a two-rule payload is a valid MULTIPLE protective order. The documented contract differs. A mock-token branch returning protection success does not validate real broker protection. See [Upstox GTT API](https://upstox.com/developer/api-documentation/place-gtt-order/). Verify protection against broker-observed orders and actual position quantity.

5. **There is no implemented owner authentication on the reviewed API.** [auth.controller.ts](/Users/user/Documents/Projects/TRADING-BOT/apps/api/src/auth/auth.controller.ts:9) returns a fixed owner identity; [main.ts](/Users/user/Documents/Projects/TRADING-BOT/apps/api/src/main.ts:8) registers no authentication guard. Trading, risk, configuration and sign-off controllers are unguarded. JWT/MFA configuration fields do not implement login or authorization. The default listener and Docker port publication can make this relevant outside the local app. Implement owner authentication/authorization on HTTP and WebSocket access and enforce it on mutations.

6. **A supposedly false live flag becomes true.** [schemas.ts](/Users/user/Documents/Projects/TRADING-BOT/packages/contracts/src/schemas.ts:51) uses `z.coerce.boolean()` for `LIVE_EXECUTION_ENABLED`. It applies JavaScript truthiness: the strings `"false"` and `"0"` parse to `true`; an omitted value defaults to false. The same issue affects `MFA_ENABLED`. A local probe reproduced this behavior. The live flag alone is not sufficient to place a trade, but it can unintentionally remove one protective gate. Parse an explicit allowlist of string boolean values and reject invalid values.

7. **DISARMED is not a shared execution gate.** [RiskService](/Users/user/Documents/Projects/TRADING-BOT/apps/api/src/risk/risk.service.ts:72) changes its local display state and `armedUntil`; [RiskReservationManager](/Users/user/Documents/Projects/TRADING-BOT/apps/api/src/risk/risk-reservation.manager.ts:80) checks kill switch, capital and risk but does not check ARMED state or expiry. Daily Bot's explicit start consent authorizes paper entries, but the wider DISARMED claim does not enforce the documented account-wide invariant. Unify mode, consent, arming expiry and kill switch at the execution boundary. Disarming must prevent every relevant entry path.

**High-priority data and strategy findings**

8. **Market quotes and option chains contain manufactured values without strong provenance.** [upstox-market-feed.service.ts](/Users/user/Documents/Projects/TRADING-BOT/apps/api/src/market-data/upstox-market-feed.service.ts:87) seeds fixed index/option prices, volumes and OI with current timestamps and `isStale:false`. With no token it reports `CONNECTED` for a virtual connection. [InstrumentCatalogService](/Users/user/Documents/Projects/TRADING-BOT/apps/api/src/instruments/instrument-catalog.service.ts:117) constructs option identifiers such as `NSE_FO|NIFTY_<date>_<strike>_CE` rather than loading broker instrument tokens; [option-chain fallback](/Users/user/Documents/Projects/TRADING-BOT/apps/api/src/instruments/instrument-catalog.service.ts:228) invents prices, 54,000 volume and 42,000 OI and marks them non-stale. A dynamically generated ladder is still synthetic. Use the authoritative broker instrument master and mark each value LIVE, DELAYED, SIMULATED or UNAVAILABLE with source and exchange timestamp.

9. **Contract dates, lot sizes and charges are outdated.** The [catalog](/Users/user/Documents/Projects/TRADING-BOT/apps/api/src/instruments/instrument-catalog.service.ts:25) generates Thursdays and includes the fixed date 2026-10-15; it generates weekly-style expiries across several underlyings. NSE currently specifies Tuesday weekly expiry for NIFTY and last-Tuesday monthly expiry for BANKNIFTY. See [NSE NIFTY specifications](https://www.nseindia.com/static/products-services/equity-derivatives-nifty50) and [NSE BANKNIFTY specifications](https://www.nseindia.com/static/products-services/equity-derivatives-banknifty).

   [lot-size.ts](/Users/user/Documents/Projects/TRADING-BOT/packages/domain/src/lot-size.ts:5) uses NIFTY 25, BANKNIFTY 15, FINNIFTY 25 and MIDCPNIFTY 50. The current published broker table lists 65, 30, 60 and 120 respectively. Contract-specific broker metadata must remain the authority. See [current index lot sizes](https://support.zerodha.com/category/trading-and-markets/trading-faqs/f-otrading/articles/lot-size-for-index-derivatives).

   [charges.ts](/Users/user/Documents/Projects/TRADING-BOT/packages/domain/src/charges.ts:37) uses option STT 0.1% and NSE exchange fees 0.0505%. Upstox's current dated table lists option premium STT 0.15% from 1 April 2026 and NSE options transaction fees 0.03553% from 1 March 2026. This affects estimated risk, trailing profit targets and P&L. The UI's “calculated live per statutory rules” label describes hardcoded constants. See [Upstox charges](https://upstox.com/brokerage-charges/).

10. **Reported funds and profit are not reliable.** [Upstox funds](/Users/user/Documents/Projects/TRADING-BOT/apps/api/src/broker/upstox-broker.adapter.ts:94) return ₹10,000 when there is no token or the request fails. `available_margin || 10000` also changes a genuine zero balance into ₹10,000. This is not a verified cached balance. Fail closed on unknown live funds and preserve zero.

    [ReportsService](/Users/user/Documents/Projects/TRADING-BOT/apps/api/src/reports/reports.service.ts:30) adds SELL proceeds (`fillPrice * fillQty`) as gross profit without subtracting entry cost. Example: buy at ₹100, sell at ₹90, 25 units should yield −₹250 gross; this code reports ₹2,250 gross. After a BUY with no SELL it inserts ₹350 realized profit. It also invents default trades/wins, ₹45 drawdown and ₹3,062.50 deployed capital. It reads the paper adapter regardless of the reported system mode. Rebuild reporting from matched confirmed fills and distinguish paper reports from broker account reports.

11. **Backtest P&L does not use historical option prices.** [backtest-engine.ts](/Users/user/Documents/Projects/TRADING-BOT/packages/domain/src/backtest-engine.ts:310) estimates premium as 0.55% of index open; [exit modeling](/Users/user/Documents/Projects/TRADING-BOT/packages/domain/src/backtest-engine.ts:190) fixes option delta at 0.5. It does not use actual option contracts, IV/theta/expiry changes or historical executable option prices. Even when index candles are genuine, the option performance is modeled. On fetch failure, [historical fallback](/Users/user/Documents/Projects/TRADING-BOT/packages/domain/src/backtest-engine.ts:519) produces random candles. That path does identify `MARKET_CALENDAR_SIMULATION`, but frontend success text still says real exchange candles. No profitability conclusion should be drawn from these results.

12. **Backtests and running bots evaluate different strategies.** The backtester evaluates `astConfig`; [AgentToolsService](/Users/user/Documents/Projects/TRADING-BOT/apps/api/src/agents/agent-tools.service.ts:215) invokes the legacy EMA/RSI evaluator. This also applies to Daily Bot's strict workflow. Custom/template entry logic can therefore be ignored during execution. A local probe supplied an explicitly false AST entry condition and still received a passing BUY_CALL proposal with confidence 0.93. The evaluator can return BUY_CALL for a PE candidate; Daily Bot blocks disallowed instrument types, but that is not equivalent to correct bearish strategy evaluation. Execute one canonical strategy representation across backtest, paper and live paths.

13. **Backtest execution assumptions materially distort results.** [Exit ordering](/Users/user/Documents/Projects/TRADING-BOT/packages/domain/src/backtest-engine.ts:195) uses a candle's high to tighten a stop before checking its low, and checks a target before an initial stop when both could have been touched. Intrabar chronology is unknown. Same-bar re-entry can use the candle open after an exit inside it. Open trades remaining at the dataset end are omitted from final performance.

    Changing AST stop/target values from 1 to 1000 and AST cutoff to 09:30 produced identical trades in a probe: several configured exit rules are not honored. Model affordability and all-in risk before entry; use conservative intrabar handling or finer-grained prices, honor configured exits, and value open exposure at the end.

    **Affordability improvement observed during review:** the initial code forced one lot even with insufficient funds; a ₹1-capital probe produced a ₹3,467.75 modeled purchase. The concurrently edited [sizing](/Users/user/Documents/Projects/TRADING-BOT/packages/domain/src/backtest-engine.ts:315) now skips unaffordable entries and adds an initial-capital check. That specific forced-lot bug is no longer an outstanding finding in the inspected working copy. This change does not correct synthetic premiums or the other execution assumptions above.

14. **Strategy indicators, templates and versioning need corrections.** [VWAP](/Users/user/Documents/Projects/TRADING-BOT/packages/domain/src/indicators.ts:82) never resets at the trading-day boundary; two daily price/volume observations of 100 and 200 produce 150 on day two rather than session VWAP 200. The [ORB template](/Users/user/Documents/Projects/TRADING-BOT/packages/domain/src/strategy-templates.ts:502) uses a rolling prior-three-bar range, rather than freezing the opening session range. Runtime observed candles are always 5m despite configurable strategy timeframes.

    [Strategy hashing](/Users/user/Documents/Projects/TRADING-BOT/packages/domain/src/strategy-version.ts:9) omits `astConfig`, maximum daily trades and cost budget. Actual rules can change while the version hash remains unchanged. Version every execution-affecting field and invalidate approvals/results when the strategy changes.

15. **Operational readiness claims include invented evidence.** [GoLiveChecklistService](/Users/user/Documents/Projects/TRADING-BOT/apps/api/src/orders/go-live-checklist.service.ts:23) starts nine of ten checks as passed, including owner consent, IP binding, protection and reconciliation. Token validity is the main dynamically refreshed item. The [worker](/Users/user/Documents/Projects/TRADING-BOT/apps/worker/src/worker.service.ts:36) claims a leader lock by assigning `isLeader = true`; its reconciliation merely logs zero discrepancies. It performs no database lock or broker read there. Broker health similarly hardcodes IP match, connection and latency. These strings are assertions, not evidence from a running system. Derive readiness from current measured checks and persist verifiable sign-offs.

16. **Live operational state and deployment are incomplete.** Standard [orders/positions APIs](/Users/user/Documents/Projects/TRADING-BOT/apps/api/src/orders/orders.service.ts:20) use PaperBrokerAdapter even when live execution is selected elsewhere. Token storage and broad order/risk/approval state are process-local; the PostgreSQL schema is not evidence of a durable runtime order ledger. Daily Bot has its own durable JSON store, which is a real improvement, but it does not make the legacy live ledger durable or provide cross-process leadership.

    Production Node startup fails on extensionless ES module imports. The API build also does not emit the `.proto` resource next to the compiled decoder, whose loader expects it there. Fix packaging and prove the exact deployed commands start and recover correctly before counting build success as deployment readiness.

17. **The live market-feed contract differs from the local decoder.** The [local proto](/Users/user/Documents/Projects/TRADING-BOT/apps/api/src/market-data/proto/MarketDataFeed.proto:39) defines flat FullFeed fields and old-style depth names; the [decoder](/Users/user/Documents/Projects/TRADING-BOT/apps/api/src/market-data/protobuf-decoder.service.ts:66) reads `fullFeed.ltp` and `fullFeed.marketLevel`. Upstox's documented V3 full feed contains `fullFeed.marketFF.ltpc`, nested OHLC, and `bidP`/`askP` depth fields. [Subscription code](/Users/user/Documents/Projects/TRADING-BOT/apps/api/src/market-data/upstox-market-feed.service.ts:365) also sends a text frame although the documented request is binary. These differences undermine the claim that the genuine full feed is working. See [Upstox V3 market feed](https://upstox.com/developer/api-documentation/v3/get-market-data-feed/). Existing [decoder tests](/Users/user/Documents/Projects/TRADING-BOT/apps/api/src/__tests__/market-data.spec.ts:17) encode and decode using the same local schema; that round trip cannot prove compatibility with broker wire data. Replace the schema with the official version and verify representative genuine-format packets, including index feeds, option depth and market status.

18. **Broker read failure can be mistaken for successful reconciliation.** [BrokerReconciliationService](/Users/user/Documents/Projects/TRADING-BOT/apps/api/src/broker/broker-reconciliation.service.ts:53) initializes remote orders/positions to empty arrays and catches remote read exceptions without distinguishing unavailable data from confirmed empty data. With an empty local ledger, a failed broker read can produce no discrepancies. A CLEAN result must require successful complete reads; otherwise status must remain unknown/degraded and entries blocked.

**Daily Bot specifically**

The backend [supportedModes](/Users/user/Documents/Projects/TRADING-BOT/apps/api/src/daily-bot/daily-bot.service.ts:156) contains PAPER only. [Start](/Users/user/Documents/Projects/TRADING-BOT/apps/api/src/daily-bot/daily-bot.service.ts:259) rejects live modes; its execution service injects PaperBrokerAdapter and repeats the paper-mode check. The frontend disables unavailable modes.

Its paper path does implement useful safeguards: immutable saved setup snapshots, durable intent checkpoints before dispatch, confirmed simulator fill checks, fresh quote/entry-window checks, shared account risk reservation, signal deduplication, trailing stops that do not loosen, continued protection after pausing, retained exposure on failed exits, and restart recovery of confirmed paper positions. The tests exercise these behaviors.

Daily Bot requests `strictMarketData:true` and uses a separate observed/verified candle store. It explicitly excludes the manufactured analytical candle seed; it would be incorrect to claim that its strict entries directly trade on those seeded candles. However, “verified” here describes local feed-observed bars, not independent certification of exchange history. Its strategy mismatch, fabricated catalog and live-feed compatibility still need correction. Missing depth also becomes bid/ask equal to LTP in [normalization](/Users/user/Documents/Projects/TRADING-BOT/apps/api/src/market-data/protobuf-decoder.service.ts:140), which must not be interpreted as executable option liquidity.

**What “hallucination” means in this code**

The reviewed agent path is deterministic service code, not an implemented LLM reasoning integration. EMA/RSI and rule arithmetic are real calculations. The [confidence value](/Users/user/Documents/Projects/TRADING-BOT/packages/domain/src/strategy-evaluator.ts:235) starts at 0.72 and adds fixed bonuses; 0.93 is not a validated 93% chance of winning. Manufactured startup agent tasks and readiness messages can look like analysis that happened even though it did not. Treat unsupported claims such as “confirmed”, “verified”, “real” and “protected” as data-integrity defects, independent of whether an AI model is involved.

**Practical completion order**

1. Keep real-money execution disabled; fix boolean parsing, API authentication, shared arming checks and false UI confirmations first.
2. Replace generated instruments/quotes and unknown-funds fallbacks with authoritative broker data and explicit provenance. Correct the actual V3 wire protocol and contract metadata.
3. Unify strategy entry/exit logic and fix version hashing, indicators, charges and fill-based P&L. Clearly identify simulation in every report.
4. Build a broker-confirmed order/position/protection lifecycle with partial fills, timeouts, retained ambiguous risk, durable state and real account leadership.
5. Validate on genuine option data and broker sandbox, then sustained paper sessions using the same strategy engine. Exercise disconnections, API rejection, crash/restart, partial fill, protection failure and emergency exit.
6. Reassess readiness based on those results. The current ₹4,000 daily objective is a configured aspiration, not supported earnings evidence.

Until these are completed, use the project as a development and paper-simulation environment. Its current screens, win rates and P&L cannot be relied on to make or supervise real-money trades.
